# SEC013 persistent storage quota design

Status: source audit and proposed implementation only. No quota enforcement or storage migration has been applied. SEC016 upload buffering files remain frozen for the current integration batch.

## Verified gap

`channels/#channel_id/attachments.ts` limits pending cloud slots to 32 and retained cloud rows to 512, with staging byte bounds. Those queries do not count posted clone destinations, multipart message uploads, avatars or orphaned files. `Storage` exposes unmetered `set`, `clone` and `move`; the current source contains 30 calls to these operations. There is no `SaveFile` implementation in this checkout: the API entry points are `uploadFile`, `uploadMessageFiles` and `handleFile` in `src/util/util/cdn.ts`.

| Path                                                                       | Current storage behavior                                         | Quota requirement                                                                                                 |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Cloud PUT                                                                  | Authorizes a CloudAttachment and writes under its uploadFilename | Trusted uploader ownership; staged bytes remain charged after posting                                             |
| Clone to message                                                           | Copies staging object into a message path; source remains        | Charge a distinct destination in addition to the source; repeated destination replacement must reserve peak bytes |
| Multipart messages, threads, webhooks, system DMs                          | API sends internal shared signature, no uploader metadata        | Propagate authenticated principal from API; webhook token maps to a durable webhook/application storage principal |
| User and guild avatars, icons, banners, emoji, stickers, sounds and events | Internal signature; hashes often create new historical objects   | Explicit principal; old hashes and failed API saves stay charged until physical removal                           |
| Store art and badges                                                       | Administrator writes local objects                               | Instance-managed assets, separate from upstream cache                                                             |
| Upstream decorations and other mirrors                                     | `fetchUpstreamAsset` writes cache on GET                         | Instance bytes plus finite cache sub-budget; cache hits do not duplicate charges                                  |
| Harvest exports                                                            | API directly calls the same storage singleton                    | Account export category and instance bytes; no bypass through the API process                                     |
| Legacy migration and avatar rehash                                         | Moves paths; S3 implements move as copy then delete              | Reserve copy peak; transfer object identity/ownership on confirmed move                                           |

FileStorage strips metadata through ExifTransformer before renaming a temporary file, so input buffer length and CloudAttachment.size are not authoritative stored byte counts. Reflink clones must conservatively count the full logical destination size: operating-system block sharing can disappear later. S3 copy creates another object; versioned buckets can retain old versions after PUT or DELETE. `exists` and `get` cannot establish successful S3 deletion because they currently collapse some storage errors into false/null.

Attachment entity removal has a BeforeRemove hook, but database cascades and bulk deletes must not be assumed to invoke it. Cloud deletion currently removes tracking rows before physical deletion, and some API cleanup removes rows in finally. A ledger must survive these row deletions. Do not infer physical release from disappearance of an Attachment or CloudAttachment.

## Ledger and admission

Add persistent `storage_quota_accounts`, `storage_objects` and `storage_operations` tables. Quota account keys include the instance and a stable principal (`user`, `webhook`, `application`, or `system`), with bigint used/reserved counters. Object identity includes provider namespace, normalized path and, for S3, retained version identity. Objects contain measured bytes, principal, category, operation generation and lifecycle state. They are independent of message/user foreign-key cascades. Operation records contain an idempotency key, expected upper bound, source/destination identities and recovery state. Never use JavaScript Number for arithmetic on SQL bigint totals without a checked safe conversion.

For every write, lock the instance quota account, then principal account, then affected object records in a fixed order. In a short transaction check `used + reserved + required <= limit` and persist the reservation and operation intent before touching storage. Never hold database row locks during file or network I/O. All CDN/API workers share these database counters; a process-local semaphore is insufficient. Zero-byte files still consume object-count admission to prevent inode/row exhaustion. Preserve SEC016 memory admission independently.

Perform storage I/O under a durable operation generation. Stat the completed local object or HEAD the returned S3 version, finalize its actual bytes and release only unused reservation in another transaction. The storage adapter must guarantee transformed output does not exceed its reserved upper bound, aborting the temporary write if it does. Clone reserves source measured bytes. A replacement reserves the complete new object while the old object is still charged; a local atomic rename retires the old bytes only after its successful result is recorded. Unique operation/path state prevents competing replacements, retries and delete races from decrementing twice.

An uncertain result or process crash leaves its reservation charged and object state recoverable. Expiration alone cannot release bytes: storage may have committed after a network timeout. Recover by checking the specific generation/object/version and finalize it, or release after positively confirming cleanup. Failed cleanup stays charged. A missing local object (ENOENT) can be confirmed; permission or I/O failures cannot. Deletes release bytes only after confirmed removal of the charged object/version and a generation check. Deleting a staging object releases that staging charge alone; posted clones remain charged.

Existing object reuse at the same identity adds no duplicate instance charge. Reading another user's object creates no ownership transfer. A new clone has a new charge; the destination actor owns it, carried by authenticated API metadata and validated independently of the source uploader. Legacy and source principal cannot be guessed from a guild/channel path. Signed internal identity headers are accepted only after existing internal request authentication; ordinary public uploads cannot select the principal. Missing internal principal fails closed except for explicitly registered system writers. Category selection is server-owned.

## Legacy inventory and backend limits

Run a paginated, checkpointed, read-only inventory of local files or S3 objects/versions. Do not follow local symlinks outside the configured root. Import measured sizes and assign ownership only when trusted database references establish it; otherwise use `legacy-unattributed`. Include orphan files, old hashes, temporary files and retained versions in instance usage. Separate local managed store art from `collectibles-shop-upstream` and other mirror namespaces; neither can disappear from global accounting. No existing object is deleted by migration or reconciliation.

Gate new mutations until inventory completes for the configured storage namespace, while keeping existing reads available. Migration creates empty ledger state as `inventory-required`, never an apparently empty usable quota. Coordinate a maintenance interval for the initial inventory; subsequent bounded reconciliation uses operation generations/checkpoints to avoid overwriting concurrent reservations. Inventory failure retains the gate and exposes a sanitized diagnostic. An over-quota legacy instance remains readable and permits confirmed deletion, but blocks growth. Ownerless bytes remain visible and charged, rather than silently exempted.

For the first S3 enforcement release, verify bucket versioning is disabled and account existing versions from inventory. If versioning is enabled or its state is unknown, fail closed for new writes unless a version-aware adapter and inventory are implemented. Simply treating a delete marker as reclaimed capacity is invalid. Local application-managed byte quotas bound object lengths conservatively; they cannot promise an exact filesystem free-space limit including filesystem metadata, external writes or unrelated services. Add a local free-space reserve check without replacing the ledger.

## Configuration and administrator controls

Proposed finite defaults for review: 100 GiB instance object bytes, 10 GiB per user, 1 GiB shared upstream cache, 100,000 instance objects and 10,000 per principal. Validate positive integer byte/count limits, with no zero-as-unlimited setting. Instance/account admission applies to managed art, exports, clones, uploads and all cache writes; cache additionally obeys its sub-budget. A webhook/application receives a bounded principal instead of charging all token posts to its creator and enabling a shared-budget denial of service. Administrator-created instance art uses the finite system principal. Exact default sizes and webhook ownership policy need parent approval before implementation.

Expose administrator-only usage and reconciliation status, quota configuration and bounded reconcile scheduling under existing admin rights. Show used/reserved bytes and object counts, account/category breakdown, unknown legacy bytes, last successful inventory and pending failed operations. Lowering a limit below current usage blocks growth without deleting content. Quota failure returns a stable explicit capacity error (413); missing inventory/invalid configuration returns 503. No automatic eviction or removal of existing art, local mirrors, files or decoration caches in this issue.

New entities, exports and PostgreSQL migration; new `src/cdn/util/storageQuota.ts` ledger and adapter operation/recovery helpers; `Storage.ts`, `FileStorage.ts`, `S3Storage.ts` measurement contracts; `CdnConfiguration.ts` finite settings. Add transaction/concurrency tests before route integration.

Once SEC016 is committed: attachment PUT/internal POST/clone/delete and legacy move; API `cdn.ts` trusted ownership propagation, message/threads/webhook/system upload callers and CloudAttachment reservation/cancellation paths. Preserve all current signature checks, max file sizes, zero-byte support and delete-race guarantees.
3. Remaining image/audio/store writers and all handleFile callers (38 current occurrences), harvest exports, cache helper and migration/rehash paths. Central metered storage wrapper must reject any unclassified writer so one omitted route cannot bypass the instance bound. Static read-only public assets outside the writable storage backend stay outside this quota.
4. Bounded inventory/reconciliation command and administrator API/UI with existing permissions; documentation and disposable live quota proof. Coordinate admin UI ownership with parent before editing it.

No attachment byte ledger helper should be shipped alone as if it fixes aggregate storage: the central wrapper, owner propagation, legacy gate and all writers are required for that claim.

## Required evidence

PostgreSQL tests must show concurrent workers cannot oversubscribe either instance or principal limits; rejected mutations never call storage; duplicate retries charge once; clone source and destination both count; destination-owner quota applies; EXIF output size is measured; overwrite peak is reserved; same-path reuse has correct ownership; zero-byte object counts are bounded. Inject failure before/after each filesystem/database step and prove uncertain writes retain capacity, restart recovery is conservative, successful deletion releases once, failed deletion releases nothing, and row cascades do not release object bytes.

Inventory fixtures must include legacy staged/posted clones, historical avatar hashes, orphan objects, cache and local managed art, temporary files, backend errors and escaping symlinks. Prove failed/incomplete inventories block mutations, over-quota legacy files survive, and read/delete still work. S3 fixtures must cover retained versions and failed HEAD/delete without false release. Finally exercise small finite quotas on disposable accounts/objects through public upload, multipart message, clone/repost, avatar, webhook, remote-media import and cache paths, checking actual files and durable totals. Clean up only those disposable objects.
