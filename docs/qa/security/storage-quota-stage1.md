# SEC013 stage 1: persistent ledger

This batch adds the ledger, finite configuration defaults and an independent storage adapter contract. Existing Storage/FileStorage/S3Storage instances and route writes are unchanged. This is not deployed quota enforcement and does not yet resolve SEC013 by itself.

The migration creates three tables with no foreign-key cascades to users, messages or cloud slots: quota accounts, objects and operation intents. All counters use SQL bigint and JavaScript bigint. Instance, principal and cache accounts lock in a fixed order. Reservations commit before storage I/O; finalization records measured output bytes. Replacement reserves the entire incoming object while the prior object remains charged. Object slots are reserved even for zero-byte files. Unique operation identities make reservation/finalization retries idempotent and reject changed identities.

Failed transaction admission rolls back counters, intent and object placeholder together. Storage success followed by database failure remains reserved for explicit recovery. Cancellation requires an adapter proof that the destination remained unchanged; uncertain results retain their reservation. Deletion first marks the tracked generation as deleting, releases database locks, performs adapter removal, and only then releases counters. Failed removal stays charged and supports retry; pending writes and mismatched generations block deletion. Unknown paths cause no physical deletion or ledger credit. Legacy objects cannot be overwritten under a new attacker principal.

Every account defaults to `inventory-required`. There is deliberately no public method to mark accounts ready or reset their counters. The upcoming inventory/provisioning layer must establish instance totals and principal ownership before admission. New trusted principals created after the inventory epoch need explicit provisioning; they are currently gated. Lowering finite limits below usage blocks new admission and permits tracked, confirmed removal. Defaults are 100 GiB instance, 10 GiB principal, 1 GiB cache, 100,000 instance objects and 10,000 principal/cache objects.

`QuotaStorageAdapter` requires generation-preserving writes/clones, actual output sizes within the supplied upper bound, generation-specific removal and a trustworthy unchanged proof. It must never implement these proofs through the existing error-swallowing `get`/`exists` methods. Existing adapters do not satisfy this contract yet. No writer should use the coordinator until its adapter and namespace inventory are complete. Versioned S3 requires version-aware operations and inventory; the first simpler implementation may gate it and require a positively verified non-versioned bucket.

The next batches still need strict adapters; complete trusted uploader/principal propagation; all storage writers including clones, caches, exports and migrations; legacy inventory/reconciliation; operation recovery and bounded completed-intent retention; config invalidation across workers; admin controls and live disposable proofs. Completed-intent pruning must preserve retry semantics and never release pending bytes by age. No quota enablement claim is appropriate before these are complete.

Validation: `scripts/tests/storage-quota.test.cjs` passed 17/17 with real PostgreSQL transactions in a uniquely named temporary schema on the isolated local `fosscord_codex_admin` database. The test creates and drops only its own schema. It verifies 12 simultaneous transactions cannot oversubscribe instance capacity; separate principal/cache budgets; zero-byte object counts; duplicate replay; peak replacement; measured finalization; conservative oversized result handling; rollback proof; unknown-owner/inventory gating; storage and database failure injection; clone charging; pre-storage rejection; failed deletion/retry; generation checks; and lower-limit behavior. TypeScript no-emit checking and targeted ESLint passed. No existing files, users or storage objects were deleted.

Run the PostgreSQL regression with `STORAGE_QUOTA_TEST_DATABASE` set to the approved local isolated database and `node --test scripts/tests/storage-quota.test.cjs`. Without that variable the database test is explicitly skipped; the configuration test still runs. Never point it at production.
